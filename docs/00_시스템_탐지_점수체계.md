# RADA 탐지·판단·점수체계 (전체 레퍼런스)

> **이 문서의 목적**: RADA 가 "어떻게 이상을 탐지해 점수를 매기고 사용자에게
> 전달하는가" 의 단일 참조본. 코드를 모르는 사람도 판단 근거를 추적할 수 있게 한다.
>
> ⚠️ **갱신 규칙**: 아래가 바뀌면 **반드시 이 문서를 같이 갱신**한다.
> - 점수/임계값(`ml_server/config_yaml/scoring_policy.yaml`)
> - 신호 정의/임계값(`ml_server/scorer/signal_extractor.py`)
> - 카테고리 점수 매핑(`ml_server/scorer/indicator_calculator.py`)
> - verdict/게이팅(`ml_server/scorer/verdict_classifier.py`, `network_only_cap.py`)
> - AI 프롬프트/스키마(`ml_server/agent/claude_api_agent.py`, `mock_agent.py`)
>
> **기준 버전**: `scoring-v0.8.0` (scoring_policy.yaml `version`). 본 문서 최종 갱신 2026-06-02.
> 값이 코드와 어긋나면 **코드가 진실(SSOT)** — 발견 시 이 문서를 고친다.

## 1. 탐지 → 전달 흐름 (큰 그림)

```
[각 PC: rada_client.exe]   40대 (60-808 호실)
      │  5초마다 메트릭 수집 (CPU/메모리/GPU/네트워크/프로세스/외부연결/per-core 등)
      │  HTTPS POST (API key 인증)
      ▼
[Spring Boot  :8080]   수신·검증·저장 게이트키퍼
      │  /analyze 로 메트릭 전달
      ▼
[ML 서버 (FastAPI) :8000]   ── 4단계 판단 엔진 ──
      │   Layer1 신호추출 → Layer2 카테고리점수 → Layer3 컨텍스트보정 → Layer4 verdict
      │   (+ ML 이상탐지 IsolationForest, retrieval 유사사례, 카테고리 게이팅)
      │   verdict 가 MEDIUM↑ 이면 AI(Claude) 호출해 자연어 판단/조치 생성
      │  결과 JSON 반환 (verdict, scores, alerts, agent 등)
      ▼
[Spring Boot]  저장 정책 적용
      │   anomaly_history     ← MEDIUM/HIGH 만 저장 (P0-1: LOW/OBSERVE 는 버림)
      │   ai_judgment_history ← AI 판단(reason/action/severity) 저장
      │   metrics_history     ← 원천 메트릭(감사용)
      ▼
[PostgreSQL]  ←읽기 전용→  [Grafana :3000]   허니콤/리본/피드 대시보드로 운영자에게 표시
```

**사용자에게 최종 전달되는 것**: Grafana 대시보드의 (1) PC별 상태 색(정상/관찰/의심/위험),
(2) 이상 탐지 피드(verdict + 점수 + 근거), (3) **AI 판단 멘트**(reason=근거, action=조치).
LOW/OBSERVE 는 저장되지 않으므로 화면에 뜨지 않는다(노이즈 억제).

## 2. 최종 판단 체계

### 2-1. 최종 점수(final_score) 계산 순서

```
신호(True/False) ──Layer2──▶ 9개 카테고리 점수 합 = raw_score
                              gpu_mining + cpu_mining + stealth + exfil
                              + process + dos + backdoor(=0) + mem + ml
        │
        ├ 컨텍스트 배수: 게임 ×0.4, 컴파일 ×0.5  (process 점수는 배수 면제)
        │   adjusted = process + (raw − process) × 배수      (음수면 0 으로 clamp)
        ▼
   누적 가중 평균 (최근 5건, score_history_store)  =  final_score
        ▼
   임계값 비교 → verdict
```

> ★ **중요**: `final_score`(=verdict 를 정하는 점수)는 위 **9개 legacy 카테고리 합**으로
> 결정된다. 응답의 `scores.score_breakdown`(resource/network/process/episode/correlation/
> ml/retrieval 8키)은 **같은 신호를 다르게 분해한 "표시·근거·게이팅용" 값**으로,
> 현재 final_score 에 직접 더해지지 않는다(§3C 참고). 둘을 혼동하지 말 것.

### 2-2. verdict 임계값 & severity (scoring_policy.yaml `thresholds`)

| final_score | verdict | overall_severity | 저장(Spring) | 의미 |
|---|---|---|---|---|
| < 5 | NORMAL | NORMAL | ✗ | 정상 |
| ≥ 5 | OBSERVE | LOW | ✗ | 관찰 (화면 미표시) |
| ≥ 9 | SUSPICIOUS | MEDIUM | ✓ | 의심 |
| ≥ 14 | HIGH_RISK | HIGH | ✓ | 위험 |

- `CONFIRMED_MINING`(채굴 확정)은 별도 verdict 가 아니라 **HIGH_RISK 로 통합**되고
  `alerts[0].type = CONFIRMED_MINING` 으로 표현된다(process 점수 ≥ 10 일 때).

### 2-3. verdict 를 바꾸는 보정 레이어 4종 (순서대로 적용)

1. **카테고리 게이팅(category_gating)** — 행동 기반 별도 경로. resource/network/system
   카테고리 이상 + 지속시간(sustained)으로 verdict 산출 후, **더 강한 verdict 채택(OR)**.
   - mining_confirmed: 3카테고리 + 180분 지속 → HIGH_RISK
   - suspicious: 2카테고리 + 30분 → SUSPICIOUS / observe: 1카테고리 + 5분 → OBSERVE
2. **승격 게이팅(promotion_gating)** — 단일 신호로 MEDIUM/HIGH 진입 차단(**강등**).
   - HIGH 유지 조건: active_signal ≥ 4 **and** category ≥ 2 (미달 시 SUSPICIOUS/OBSERVE 로 강등)
   - SUSPICIOUS 유지 조건: active_signal ≥ 3 **and** category ≥ 2 (미달 시 OBSERVE)
   - **fast-path 면제**(즉시 유지): `mining_known`(process≥10) / `confirmed_sustained`(게이팅
     mining_confirmed) / `alerts_contain_confirmed_mining`
3. **네트워크 단독 캡(network_only_cap)** — 네트워크 신호만 활성이고 자원/시스템
   시그니처·강한 프로세스 근거가 없으면 **verdict 를 OBSERVE 로 캡**(PID 귀속 없는
   EXFIL/DOS FP 차단). 면제: known_miner / mining_pool_ip / external_conn_suspicious_owner
   / single_core_full / process_recreation / 자원·시스템 신호(_RES_SYS).
4. **컨텍스트 감점(context_discount)** — startup/보안스캔/업데이트 등 정황 시 감점(§3D).

> 추가 해석 레이어(ADDITIVE, **점수 미반영**): `risk_vector`(채굴/오작동/노후화/위협
> 4축 재투영), `signal_quality`(신호 측정 품질), `explanation_confidence`(설명 신뢰도),
> `retrieval_evidence`(유사 과거사례). 모두 운영/AI 참고용이며 verdict 를 바꾸지 않는다.
> (retrieval 은 FP-fix #4 로 score 기여 0 고정.)

## 3. 점수 상세 — "정보마다 몇 점인가" (0점 포함)

### 3A. 신호(Signal) 목록과 탐지 임계값

`signal_extractor.py` 가 매 요청마다 산출하는 원자 신호(True/False). **신호 자체는 점수가
아니며**, §3B/§3C 에서 점수로 환산된다. (history ≥ 12건=약 1분 있어야 stddev 계열 발화)

| 신호 | True 조건(임계값) |
|---|---|
| **자원(Resource)** | |
| `gpu_active` | GPU load ≥ 30% |
| `gpu_high` | GPU load ≥ 70% |
| `gpu_flat` | GPU stddev < 5 **and** gpu_active (변동 없는 고부하) |
| `gpu_cpu_gap` | GPU ≥ 70% **and** CPU < 20% |
| `vram_low` | VRAM 사용률 < 30% **and** gpu_active |
| `vram_stable` | VRAM stddev < 50MB **and** gpu_active |
| `power_stable` | 전력 stddev < 10W **and** 평균전력 ≥ 60W **and** gpu_active |
| `tensor_inactive` | 텐서코어 == 0 **and** gpu_active |
| `sm_high` | SM 사용률 ≥ 70% |
| `stealth_mismatch_power` | 평균전력 ≥ 80W **인데** 평균 GPU < 30% (전력↔부하 모순) |
| `stealth_mismatch_vram` | VRAM 사용률 > 70% **인데** GPU < 20% |
| `cpu_high` | CPU ≥ 80% |
| `cpu_flat` | CPU stddev < 5 **and** CPU ≥ 60% |
| `mem_high` | 메모리 ≥ 85% |
| `mem_critical` | 메모리 ≥ 95% |
| **네트워크(Network)** | |
| `net_external_high` / `spike_count_1m` | 외부 패킷 수 ≥ 8 |
| `persistent_ext` | 외부 패킷 수 평균 ≥ 8 (지속) |
| `mining_pool_ip` | 외부연결 IP 가 MINING_POOL_IPS prefix 일치 (**현재 목록 비어 사실상 미발화**) |
| `outbound_spike` | outbound > 평균×5 **and** > 1.0MB **and** 평균 > 0.01 |
| `dos_spike` | inbound > 평균×배수(class30/free15) **and** ≥ 100MB/5s **and** 3회 연속 |
| `net_out_sustained` | outbound ≥ max(평균×1.5, 0.5MB) **and** 평균 > 0.005 |
| `disk_write_net_out_sustained` | disk_write ≥ 1MB **and** net_out_sustained |
| `new_remote_ip_burst` | unique IP ≥ 8 **and** 중복연결 < unique |
| `external_conn_suspicious_owner` | 외부연결 소유 프로세스 경로가 appdata/temp + 비화이트리스트 (ADDITIVE) |
| **프로세스(Process)** | |
| `known_miner` | top_processes 에 MINING_PROCESSES 이름 존재 |
| `persistent_miner` | known_miner 가 history 6회 이상 등장 |
| `temp_exec` | SUSPICIOUS_PATHS(temp 등)에서 실행 + 비화이트리스트 |
| `appdata_exec` | AppData(Roaming/Local, temp 제외)에서 실행 + 비화이트리스트 |
| `exec_path_suspicious` | temp_exec **or** appdata_exec |
| `unknown_process_active` | 비화이트리스트·비마이너 프로세스가 CPU ≥ 80% |
| `mining_process_or_pool` | known_miner **or** mining_pool_hit |
| `single_core_full` | 단일코어 ≥ 90% **인데** 전체 CPU ≤ (100/코어수)×2 (ADDITIVE) |
| `process_recreation` | 동일 프로세스가 동시 ≤2 인데 PID 가 3개↑ 갈아끼며 재등장 (ADDITIVE) |
| **기타** | |
| `ml_anomaly` | IsolationForest 가중 점수 < −0.1 |
| `is_gaming` | 게임/렌더 프로세스 실행 중 (감점 트리거) |
| `is_compiling` | 컴파일/인코딩 프로세스 실행 중 (감점 트리거) |

> **측정 불가 처리**: 네트워크/프로세스 수집이 실패하면 해당 신호들을 0/False 로
> 잠그지 않고 `signals_missing` 에 표기 → "측정 불가"와 "정상 0" 을 구분(silent fail 방지).

### 3B. verdict 점수 — legacy 9 카테고리 (★ final_score 를 구동)

각 신호가 True 일 때 해당 카테고리에 가산되는 점수. **이 9개 합 = raw_score**.

| 카테고리 | 가산 규칙 (신호 → 점수) |
|---|---|
| **gpu_mining** | gpu_high `+1`, gpu_flat `+3`, gpu_cpu_gap `+3`, net_external_high `+1`, mining_pool_ip `+5`, (tensor_inactive **and** vram_low) `+3`, is_gaming `−5` |
| **cpu_mining** | cpu_high `+1`, cpu_flat `+3`, (GPU 안 바쁨) `+1`, mining_pool_ip `+5`, (GPU 비활성 **and** cpu_high **and** cpu_flat) `+2`, is_compiling `−5`, is_gaming `−3` |
| **stealth** | (전력/VRAM 모순 있을 때만) stealth_mismatch_power `+5`, stealth_mismatch_vram `+5`, vram_stable `+1`, gpu_flat `+1`, power_stable `+1`, is_gaming `−3`, is_compiling `−2` |
| **exfil** | outbound_spike `+5`, net_external_high `+1` |
| **process** | known_miner `+10`, persistent_miner `+3`, temp_exec `+1` |
| **dos** | dos_spike `+5` |
| **backdoor** | **항상 0** (P2: 정상 외부통신과 구분 불가해 verdict 승격 비활성) |
| **mem** | mem_critical `+1`, (mem_high **and** not cpu_high) `+1` |
| **ml** | ml_anomaly 시 `min(5, max(1, |ML점수|×5))`. cap=5. rule/correlation 합 0 이면 `−2` |

> 0점인 대표 케이스: backdoor 는 항상 0. 신호가 안 떠도 해당 항목 0.
> `mining_pool_ip` 는 +10(gpu+cpu)이지만 **MINING_POOL_IPS 목록이 비어 현재 미발화**.

### 3C. score_breakdown 8키 (표시·근거·게이팅용 — final_score 미반영)

응답 `scores.score_breakdown`. 같은 신호를 카테고리로 재분해해 **운영자 가독성**과
**게이팅의 category_count** 산출에 쓴다. 점수가 0 초과인 키 = "활성 카테고리".
정책값은 `scoring_policy.yaml scores`.

| 키 | 가산 규칙 |
|---|---|
| `resource` | cpu_high`+1`, cpu_flat`+1`, mem_high`+1`, mem_critical`+1`, (gpu_high&측정됨)`+1`, top_cpu_norm≥0.85`+2`/≥0.6`+1` |
| `network` | (외부연결 truncated 면 0) / spike+동반신호`+1`, net_out_sustained`+2`, outbound_spike`+2`, unique IP≥12`+2`/≥6`+1`, new_remote_ip_burst`+1` |
| `process` | known_miner`+10`, persistent_miner`+3`, temp_exec`+1`, appdata_exec`+1` |
| `episode` | dos_spike`+5`, persistent_ext`+2` |
| `correlation` | (cpu_high&net_out)`+2`, disk_write_net_out`+5`, (unknown_proc&net_out)`+5`, (appdata_exec&net_out)`+3`, mining_process_or_pool`+10`(known)/`+8`(pool) |
| `ml` | §3B ml 과 동일(cap 후) |
| `retrieval` | **항상 0** (FP-fix #4: 유사도 근거는 점수 미반영, explanation_confidence 로만 노출) |
| `context_discount` | §3D 감점 합(음수) |
| `final` | = final_score (위 2-1 결과) |

### 3D. 컨텍스트 감점 / 배수 (오탐 억제)

**배수**(legacy, raw_score 에 곱): 게임 `×0.4`, 컴파일 `×0.5` (process 점수는 면제).

**감점**(`context_discounts`, 합산 후 최대 `−4` clamp):

| 정황 | 감점 | 트리거 |
|---|---|---|
| startup | `−1` | 부팅 직후 (local_alert type 에 startup/boot) |
| security_scan | `−2` | 백신/Defender 스캔 |
| maintenance_update | `−2` | 업데이트/패치/유지보수 |
| lab_agent | `−1` | 실습실 관리 에이전트 |
| class_or_free | `−1` | 수업/자유 slot 이고 다른 감점이 전혀 없을 때 기본 1회 |

> **danger override**: 위험 신호(unknown_proc+net_out / temp·appdata+고부하 / disk_write_net_out
> / mining_process_or_pool) 가 하나라도 True 면 감점을 `−1` 까지로 약화(정상 정황으로
> 위장한 위협이 과도하게 감점받는 것 방지).

### 3E. 한눈에: 가장 무거운 신호 (단일 기여 큰 순)

| 점수 | 신호/조건 | 어디에 |
|---|---|---|
| `+10` | known_miner (채굴 프로세스 이름 일치) | process / correlation |
| `+8` | mining_pool_only (풀 IP만, known 아님) | correlation |
| `+5` | mining_pool_ip(gpu+cpu 각 5=10), outbound_spike, dos_spike, stealth mismatch, disk_write_net_out, unknown_proc_net | 다수 |
| `+3` | gpu_flat, cpu_flat, gpu_cpu_gap, persistent_miner, appdata_net | 다수 |
| `+1~2` | cpu_high, mem_*, net_external_high, unique IP 등 | 다수 |
| `0` | backdoor(고정), retrieval(고정), 미발화 신호 | — |

## 4. AI(Claude) 호출 — 입력 정보와 예상 안내 멘트

### 4-1. 호출 조건

- **overall_severity 가 MEDIUM 또는 HIGH 일 때만** 호출(`analyze_router`). LOW/OBSERVE 는
  Spring 이 어차피 저장 안 하므로 LLM 비용 낭비를 막기 위해 호출하지 않는다.
- 실제 호출 여부: 런타임 토글(`POST /agent/enabled`)로 끄면 키가 있어도 **mock** 사용(비용 0).
  꺼져있지 않고 `USE_REAL_CLAUDE`/키 설정 시 **실제 Claude** 호출. 실패하면 mock 으로 fallback.
- 모델/토큰: `CLAUDE_MODEL`(기본 claude-sonnet-4-5), `CLAUDE_MAX_TOKENS`(기본 500), tool use
  (structured output)로 항상 유효한 JSON 강제.

### 4-2. AI 가 받는 정보 (프롬프트 구성, `build_prompt`)

| 블록 | 내용 |
|---|---|
| 현재 메트릭 | PC id, 시각, 시간표 slot, CPU%, 메모리%, GPU(load/VRAM/SM/텐서/전력), 외부연결 수, Net ↑↓MB/5s |
| 전체 PC 노후화 | global_hw 감지 시 detail |
| 유사 과거 사례 | retrieval top-k (segment_id/거리/verdict/score) + peer 비교(same_slot_peers, peer_mismatch) |
| 규칙 스코어링 결과 | verdict, 최종점수, (gpu_mining/cpu_mining/stealth/exfil/process 점수), 컨텍스트배수, **활성신호 목록** |
| 해석 레이어 | risk_vector(4축), signal_quality(저하 출처), explanation_confidence(설명 신뢰도/5) |
| 탐지 알람 | alerts 목록 ([severity] type: detail) |
| 프로세스 | top 5 프로세스(name, CPU%, MEM%, path) |
| 외부연결 소유 프로세스 | 외부연결별 ip:port ← proc_name proc_path (저-CPU 백도어 식별용, #3) |

### 4-3. AI 가 반환하는 것 (`report_judgment` 도구 스키마)

| 필드 | 값 | 설명 |
|---|---|---|
| `judgment` | NORMAL / SUSPICIOUS / DANGEROUS | 종합 판정 |
| `severity` | LOW / MEDIUM / HIGH | 심각도 |
| `reason` | 한국어 1~2문장(≤120자) | **판단 근거** (사용자 표시) |
| `action` | 한국어 1문장(≤60자) | **추천 조치** (사용자 표시) |
| `hw_degradation` | NONE / SUSPECTED / CONFIRMED | 하드웨어 노후/오류 |

`is_mock`(true=mock) 도 함께 저장돼 실제 Claude 작동 여부를 구분한다.

### 4-4. 예상 안내 멘트 (mock 기준 — 실제 Claude 도 유사 톤·형식)

mock_agent 가 verdict 별로 생성하는 결정적 멘트. 실제 Claude 는 같은 입력을 받아 더
맥락화된 자연어를 쓰지만, **형식(reason/action)과 강도는 아래와 정렬**된다.

| 상황 | judgment/severity | reason(예) | action(예) |
|---|---|---|---|
| 채굴 확정(CONFIRMED_MINING) | DANGEROUS/HIGH | "채굴 의심 — 확인이 필요합니다. 프로세스 점수=10." | "해당 프로세스 즉시 강제 종료 및 관리자 현장 확인." |

| 메모리 임계(누수의심) | SUSPICIOUS/HIGH | "메모리 96% 임계 초과인데 CPU는 12%로 낮음. 메모리 누수/좀비 프로세스 가능성." | "작업 관리자에서 메모리 점유 프로세스 확인 및 종료." |

| SUSPICIOUS(일반) | SUSPICIOUS/MEDIUM | "의심 점수 10.0점. 지속 모니터링 필요." | "실행 중인 프로세스 및 네트워크 연결 상태 점검." |
| OBSERVE | SUSPICIOUS/LOW | "낮은 위험 점수 6.0점. 경미한 이상 신호." | "지속 관찰 후 패턴 지속 시 현장 확인." |
| 노후화만 감지 | SUSPICIOUS/MEDIUM | "하드웨어 노후화 징후: …" | "해당 PC 점검 예약. 발열·디스크 상태 확인." |
